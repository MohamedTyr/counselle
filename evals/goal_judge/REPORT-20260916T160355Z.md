## Note on the starting numbers

Before touching any code, the same 32-case/34-criterion gate was run twice more
against the **unmodified** judge, to characterize what was actually broken:

| Run | TP | FP | TN | FN | TPR | TNR | FPR |
|---|---|---|---|---|---|---|---|
| baseline run A (this session) | 15 | 0 | 17 | 2 | 0.882 | 1.000 | 0.000 |
| baseline run B (this session) | 14 | 0 | 17 | 3 | 0.824 | 1.000 | 0.000 |

Both runs used the **same 32 cases**, no code changed between them. TNR and FPR
were rock-solid at 1.000/0.000 across every baseline run observed this session;
only TPR moved. **The judge was non-deterministic run-to-run** — the single
biggest problem, independent of any prompt content, because a moving measurement
cannot prove a fix worked. Diagnosing the false negatives that did appear across
these runs (`test-01-school-deadline-single-met`, `test-07-essay-word-count-met`,
`test-22-prior-citation-retained-still-met`, `test-28-batch-changed-count-matches-total-met`)
showed a consistent pattern: **every one of them cited zero evidence despite a
clean `outcome=success` mutation receipt being present with the exact field/value
that satisfied the criterion.** Reading `app/goal_judge.py::_receipt_text` (before
this fix) confirmed why: it rendered only `outcome=success family=school
action=update` — the bare type/outcome/family/action tokens — and **never
rendered the receipt body's actual typed fact** (subject title, `field_key`,
the after-value). The judge was not being irrationally strict; it was
correctly reporting that the text in front of it never stated what was
changed. That is an evidence-rendering defect, not a judge-capability defect.

A single `no_change`-outcome case exists in the dataset
(`test-02-school-deadline-no-change-still-met`); it was **not** a driver of the
false negatives observed this session — it scored correctly in both baseline
runs above. The rule for it is still worth stating explicitly (framing `no_change`
as "nothing happened" is a real, if smaller, failure mode), but it is not the
centerpiece of this fix.

## The fix

**1. `app/goal_judge.py` (the more important half).** `_receipt_text` now
renders the mutation body's actual typed fact via a new `_body_fact` helper
(one branch per `MutationBody` variant — `UpdateMutationBody`,
`BatchMutationBody`, `StateTransitionMutationBody`, `DuplicateMutationBody`,
`ReorderMutationBody`, `EssayEditMutationBody`, `EssayWriteMutationBody`,
`ProfileMutationBody`, `MemoryMutationBody`, `UnresolvedMutationBody`), plus an
explicit `_OUTCOME_FRAMING` sentence per outcome stating in plain words whether
the fact is proven. Before/after for one receipt (`test-01`):

Before:
```
[s1] workspace:update_school
  outcome=success family=school action=update
```

After:
```
[s1] workspace:update_school
  outcome=success family=school action=update
  fact: "Updated State Tech deadline": deadline set to '2026-01-05'
  PROVEN: this write completed; the fact above is now true.
```

`no_change` now renders as (`test-02`):
```
  fact: "Rivertown deadline already set": deadline set to '2026-01-15'
  PROVEN: the tool checked the current state and found it already matched
  the desired outcome, so no write was needed. This is affirmative proof
  the criterion already held — not an absence of evidence.
```

A read-only `summary` step (no mutation) is now framed as equally valid
proof rather than merely appended as unlabeled context, and a receipt
carried forward from the evidence bundle via `prior_cited_step_ids` is now
marked "cited by an earlier round... and carried forward" so the judge does
not discount it as secondhand.

**2. `config/assets/prompts/goal_judge.md`** — added rules 9-12: typed receipt
fields are sufficient proof on their own (no independent prose confirmation
required), `no_change` is affirmative evidence, a read-only verification
receipt is equally valid proof, and evidence carried forward from an earlier
round counts the same as this round's. Added one worked "met" example in the
existing calibration style covering the `no_change` case end-to-end.

**3. Pinned sampling.** The judge's `Agent` (in `judge_goal` only, not
`derive_criteria`) is now constructed with
`model_settings=ModelSettings(temperature=0.0)`. This is a real behavior
change beyond prompt/rendering — flagged per the task brief's instruction —
made specifically so a score change can be attributed to the fix rather than
to sampling noise, given the run-to-run drift documented above.

## Guarding the direction that matters (regression check)

- **TNR: 1.000 (17/17), unchanged from every baseline run.**
- **FPR: 0.000 (0 false positives), unchanged from every baseline run.**
- **Adversarial subset: 6/6 correct** — `test-17` through `test-21` and
  `test-29`, all six adversarial `not_met` cases scored `met=false`
  exactly as before. The fix only changed how *true* evidence is rendered and
  interpreted; it added no leniency toward padding, restated goals, or
  confident-but-empty text, and the padding-attack calibration example and
  rules 1-8 (unchanged) still govern those cases.
- The fix did not touch `domain/goal.py`'s `compute_checked` code-level
  correction (C9/C10) — a criterion citing no valid `step_id`, or citing only
  an `"unknown"`-outcome receipt, is still forced to `met=false` regardless of
  what the judge's raw output says. The literalism fix operates entirely
  upstream of that safety net, in what the judge is shown, not in loosening
  what code accepts from it.

**No false positive was introduced anywhere in this run.** TPR moved from
sub-0.90 to 1.000 by getting real evidence rendered where it previously was
not, not by relaxing the standard of proof.

## Honesty note on the fix's own evidence

This is one clean post-fix run at n=34 with pinned sampling (temperature=0),
run immediately after the fix. A perfect TPR=1.000/TNR=1.000/FPR=0.000 on a
32-case set is a strong result but a small one — it demonstrates the specific
diagnosed defect (evidence literalism in receipt rendering) is fixed and that
the fix did not open a false-positive door, not that the judge is flawless at
scale. A second confirmation run (same pinned settings, no code changed) was
launched to verify the temperature pin actually stabilizes the measurement
rather than the first post-fix run being a lucky draw, but this session's
sandbox network was hitting repeated transient `oauth2.googleapis.com`
connection failures during every run today (visible in all three raw logs,
before and after the fix — retried and eventually succeeded in the two runs
that finished); the confirmation run did not finish within this session's
time budget and was left running rather than killed. **Recommendation:**
before treating TPR=1.000 as a stable result, re-run
`uv run python -m evals.goal_judge.runner` (temperature is now pinned in
code, so no flag is needed) at least once more outside this session and
confirm TP/FN reproduce; do not treat a single post-fix run as sufficient
proof of stability given the pre-fix drift documented above.
