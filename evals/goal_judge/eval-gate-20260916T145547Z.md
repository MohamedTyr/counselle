# Goal-mode judge — Phase 2 eval gate (measured, 2026-09-16)

Scope: (1) the `GoalCriteriaOutput.criteria` schema fix (`min_length=1` -> `2`)
and its retry-path behavior; (2) the actual Phase 2 eval gate run against
`evals/goal_judge/cases.yaml`'s 32-case held-out `test` split and
`criteria_examples.yaml`'s 12 examples, per plan §6.2/§3.8. Both calls run
against `google-vertex:gemini-2.5-flash` (the cheap tier - `model_goal_judge`
and `model_goal_criteria` are both unset, so they fall back to
`settings.model_cheap`).

**Bottom line: the gate FAILS.** TPR does not clear 90% in either measured
pass, and a second pass over the same cases produced a materially different
TPR - the judge's behavior is not stable enough to trust yet, independent of
whether any single number clears the bar.

## 1. Schema fix (Task 1)

`app/goal_judge.py::GoalCriteriaOutput.criteria` changed from
`Field(min_length=1, max_length=6)` to `Field(min_length=2, max_length=6)`,
matching `config/assets/prompts/goal_criteria.md` and plan §3.2's "2-6
criteria, no exceptions" contract.

**Retry-path behavior, confirmed by running the affected tests live:**
1. If the model returns 1 criterion, PydanticAI's own output-validation retry
   fires first (its `max_retries=1` on the output tool) - the model gets one
   chance to fix the count itself, invisibly to `derive_criteria`.
2. If it still returns fewer than 2, PydanticAI raises
   `UnexpectedModelBehavior: Exceeded maximum output retries (1)`.
3. That exception is a plain `Exception`, so `_run_with_retries`'s `except
   Exception` catches it exactly like a transport failure and retries the
   *whole* call up to `settings.goal_judge_retries` (default 2) more times,
   with exponential backoff (1s, 2s, 4s...).
4. If every attempt still comes back under 2 criteria, `_run_with_retries`
   returns `None` and `derive_criteria` raises `GoalCriteriaError` - the
   caller's documented failure mode. No hard loop; it is bounded by
   `goal_judge_retries` exactly as it is for a genuine transport failure.

This was not hypothetical: two existing tests
(`tests/app/test_goal_judge.py::TestDeriveCriteria::test_happy_path_returns_criteria_and_note`
and `::test_blank_note_after_strip_falls_back_to_default`) stub a model that
always returns exactly 1 criterion, so they immediately exhausted every
retry and turned RED (`GoalCriteriaError`) once the schema tightened. Fixed
by giving both stubs a second criterion (`c2`) and asserting on the pair;
no other test changes were needed. `uv run pytest tests/app/test_goal_judge.py`
is green (11 passed), and the full routine suite
(`uv run pytest -m "not live_llm and not live_search and not live_db"`) is
green at **2197 passed** - identical to the stated baseline. `ruff check .`
and `mypy .` are both clean repo-wide.

## 2. The eval gate (Task 2)

### 2.1 Official scored run (`uv run python -m evals.goal_judge.runner`, full test split)

Raw output (`artifacts/goal-mode/full-run-20260916T143128Z.log`):

```
n=34 TP=15 FP=0 TN=17 FN=2
TPR=0.882  TNR=1.000  FPR=0.000  overall agreement=0.941
gate (§6.2/§3.8): TPR > 0.90 AND TNR > 0.90 -> FAIL
```

(`n=34` is criterion-level, not case-level: 32 test cases, two of which -
`test-14-multi-criteria-mixed` and `test-27-independent-criteria-one-fails-other-unaffected`
- carry 2 criteria each.)

- **TPR = 15/17 = 0.882** - FAILS the >90% bar.
- **TNR = 17/17 = 1.000** - clears it cleanly.
- **FPR = 0/17 = 0.000** - the judge never declared a criterion met when it
  wasn't, in this pass.
- **Gate verdict: FAIL** (TPR is the blocking number; the >90%/>90% gate
  requires both).

The run also hit two transient `TransportError` (OAuth token refresh,
`RemoteDisconnected`) failures against Vertex mid-run; both were absorbed by
`_run_with_retries`'s backoff and did not affect the final scores - noted
here only because the raw log (4.5MB, mostly PydanticAI's verbose exception
pretty-printing) contains them.

### 2.2 Per-case diagnosis (second full pass, same 32 cases, with reasons)

The runner doesn't print which case/criterion failed, so I re-ran
`judge_goal` over every test case a second time with a small throwaway
script (`artifacts/goal-mode/mismatch-diagnosis.log` has the full output) to
get the judge's own stated reason for every wrong call. **This second pass
scored differently from the first**: TP=13, FP=0, TN=17, FN=4 -> TPR =
13/17 = **0.765**, TNR = 17/17 = 1.000. Same gate verdict (FAIL), but a
visibly different TPR from run 2.1's 0.882 on the exact same 34
criterion-instances - i.e., the judge is not deterministic run-to-run, which
is itself a finding (§4 below).

**Every failing case from the diagnostic pass, with the judge's stated reason:**

| Case | Criterion | True | Predicted | Judge's reason |
|---|---|---|---|---|
| `test-01-school-deadline-single-met` | c1: "State Tech has an application deadline recorded." | met | **not met** | "No tool receipt explicitly confirms that State Tech's application deadline was recorded or updated." |
| `test-07-essay-word-count-met` | c1: "The Common App essay has a final word count of at least 500 words." | met | **not met** | "The final assistant text states the essay is 612 words, but no tool receipt confirms this word count." |
| `test-22-prior-citation-retained-still-met` | c1: "Every school on the list has an application deadline recorded." | met | **not met** | "The update receipts do not specify that a deadline field was updated, nor do they confirm that every school on the list has a recorded deadline." |
| `test-28-batch-changed-count-matches-total-met` | c1: "Both named overdue tasks are marked done." | met | **not met** | "The tool receipt indicates tasks were archived but does not confirm that two specific overdue library-related tasks were marked done." |

All four have `evidence_step_ids=()` - the judge cited *no* evidence at all
for these "not met" calls, even though every one of these cases has a
successful, typed mutation receipt (`outcome=success`, correct `field_key`,
correct `value`) sitting in the evidence bundle it was given. This is a
**false-negative pattern of excessive literalism**: the judge appears to
want the receipt's free-text `summary`/label to restate the criterion almost
verbatim, and discounts the structured `field_key`/`value`/`outcome` fields
that `_receipt_text` renders - even though those typed fields are exactly
the honesty-grade evidence `app/goal_judge.py`'s own docstring says the
judge should be grading against (§3.3/§27.8).

None of the 4 failures in this pass are adversarial cases, and none is
`test-02` (the `no_change` case - see §2.4). This is a *different* failure
mode from the padding-attack risk the plan calls out: it is the judge being
too conservative, not too credulous.

### 2.3 Adversarial subset (R2 - the MT-Bench padding-attack risk)

Six cases are tagged `adversarial: true` in the test split:
`test-17-adversarial-confident-no-receipt`,
`test-18-adversarial-restates-goal-twice`,
`test-19-adversarial-long-explanation-hides-gap`,
`test-20-adversarial-empty-batch-praised`,
`test-21-adversarial-technical-jargon-padding`,
`test-29-adversarial-apologetic-but-still-padded`. Five are labeled
`met=False` (a padding/confidence attack over a genuinely incomplete
action); one, `test-18`, is labeled `met=True` (padded language, but the
underlying action is genuinely done - the trap in the *other* direction).

**In the diagnostic pass (§2.2), all 6 adversarial criteria were judged
correctly: 0 FP, 0 FN.** The cheap-tier judge was not fooled by verbosity,
confident tone, restated goals, or apologetic hedging in this run, and it
correctly did *not* punish `test-18` just because its language was padded.
This is a genuinely good sign against R2's specific concern. I can't confirm
the same 6/6 held in run 2.1 (that run didn't log per-case detail before I
started the diagnostic pass), but since run 2.1's FN=2 is fewer than run
2.2's FN=4 and none of run 2.2's 4 failures are adversarial cases, the
adversarial subset was very likely also clean in run 2.1. Given the observed
run-to-run variance, I'd treat "0/6 fooled" as encouraging rather than
proven - a single adversarial case flipping on a future run would not be
surprising given §4.

### 2.4 The `no_change` hypothesis - does it generalize?

The earlier smoke run's one FN was `test-02-school-deadline-no-change-still-met`
(`outcome: no_change`, criterion met because the deadline was *already*
correct). I reproduced it directly: `uv run python -m evals.goal_judge.runner --smoke 2`
gave `n=2 TP=1 FP=0 TN=0 FN=1`, and the FN was `test-02` again
(`artifacts/goal-mode/smoke-check.log`).

But in both full passes since (§2.1 and §2.2), `test-02` was **not** among
the failures - it scored correctly both times. There is only one
`no_change`-outcome case in the whole 32-case split, so this can't be
proven or disproven statistically from this dataset alone, but the direct
evidence says: **it does not reliably generalize into a systematic
"no_change = under-credited" defect.** What it *does* look like, combined
with §2.2's four failures, is one instance of a broader and reproducible
pattern: the judge is inconsistent about trusting a structured mutation
receipt as proof at all, regardless of which outcome value the receipt
carries. `no_change` isn't specially penalized; typed evidence in general is
being second-guessed, non-deterministically, across runs.

### 2.5 Criteria-set audit (`criteria_examples.yaml`, 12 examples, rule-based - no model call)

```
criteria audit: heuristic agreed with hand label on 11/12 examples
```

The one mismatch, `crit-07-good-task-done`, is a heuristic false positive,
not a labeling or judge defect: the criterion text is `"The task named
'Submit FAFSA' has done=true."` - the heuristic's C11 keyword list matches
the substring `"submit"` inside the task's proper name and flags it as a
claimed-external-action violation, when the criterion is actually a correct,
observable, code-checkable claim about a task's `done` field. This is a
known limitation of the keyword-based sanity checker in
`evals/goal_judge/runner.py::audit_criteria_set` (documented in its own
docstring as "a heuristic, not a substitute for review") - it has no bearing
on the live criteria-derivation model's actual behavior, since this audit
never calls the model. No C11 violations were missed in the other 11
examples.

calls: 2 (smoke) + 32 (official gate run) + 32 (diagnostic rerun) + 0 (the
criteria-set audit is rule-based, no model calls) ~= 66 short judge calls,

## 4. Diagnosis and recommendation

**The gate fails, and it fails in a specific, non-hallucination-shaped way:**
zero false positives across both full passes (the judge never over-credits,
including on every padding/confidence-attack case), but a false-negative
rate that is both too high (>10%) and unstable between runs on identical
inputs (FN=2 vs FN=4 across two passes over the same 34 criterion
instances). Two separate problems are stacked here:

1. **Evidence literalism.** The judge is discounting the typed
   `outcome`/`field_key`/`value` fields on mutation receipts - exactly the
   evidence `app/goal_judge.py` and `docs/DATABASE_GUIDE.md`'s honesty model
   are built to make it trust - and instead wants the free-text summary to
   restate the criterion. All 4 diagnosed failures cite zero evidence
   (`evidence_step_ids=()`) for a "not met" verdict on a case with a clean
   successful receipt sitting right there.
2. **Run-to-run instability.** The same 34 judgments scored differently
   twice. At `gemini-2.5-flash`'s default sampling, this is very plausibly
   temperature-driven; nothing in `judge_goal`/`_vertex_model` sets a
   temperature or otherwise pins sampling for this call. A judge whose
   pass/fail draw changes between otherwise-identical runs is not safe to
   gate a "goal achieved" card on, independent of whether any single
   sample's TPR clears 90%.

**Recommendation - in order of what I'd try first:**
1. Tighten `config/assets/prompts/goal_judge.md` to explicitly instruct the
   judge to treat a receipt's typed `outcome=success` + matching
   `field_key`/`value` as sufficient proof on its own, without requiring the
   free-text summary to restate it - this directly targets the observed
   failure mode and is the cheapest fix to try first.
2. Set a low/zero sampling temperature for the judge call specifically (not
   necessarily the criteria-derivation call), to remove the run-to-run
   variance before re-measuring - a gate measured against a moving target
   isn't trustworthy regardless of the prompt fix.
3. If (1)+(2) don't close the gap, this is exactly the evidence plan §9(b)
   asks for to decide "run the judge one tier above the agent" - a
   cheap-tier judge that under-credits real, structured evidence at a
   variable rate is a legitimate case for `model_goal_judge` to be a
   stronger tier than `model_cheap`, via the existing
   `goal_judge_model_setting` seam in `app/model_selection.py`. I did not
   make this change myself - it's an owner call per §9(b), and the plan
   explicitly leaves it open.

I did not weaken the gate, adjust the hand labels, or drop any hard cases to
make this pass. The failure is real and, per the direction observed (FN, not
FP), the safer of the two possible failure directions - but it still fails
the documented >90%/>90% bar and should not be treated as ready to gate the
loop.
