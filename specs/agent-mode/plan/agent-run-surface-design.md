## Problem Statement

The agent run surface renders every turn as two fixed zones — a collapsed
"Thought for Xs" drawer, then the final answer — so it reads like a RAG chatbot
(retrieve, then answer) instead of an agent working (think → say → act → say →
act → answer). Two root causes:

1. **The render flattens time.** `turn-reducer.ts` splits the stream into
   `timeline` (steps + thinking) and `blocks` (answer prose). `ChatMessage.tsx`
   (`AssistantBody`, lines 65-91) renders them as two zones: one `AgentRunView`
   drawer holding the whole timeline, then all `blocks`. The backend streams
   events in true chronological order; the frontend discards that order.

2. **Narration is filed as "thinking" and buried — and kept deliberately terse.**
   `thinking_summaries` defaults to `False` (`config/settings.py:75`), so the
   model emits **no** raw chain-of-thought. Every `thinking` event today is
   actually **narration** — the agent's "loud talk" — which `steps.py` routes
   into the `thinking` feed, styles as muted italic, and files under a "Thought
   for Xs" drawer. Two things are wrong: (a) the routing buries loud talk that
   should be inline; (b) the prompt asset **instructs** terseness —
   `config/assets/prompts/counselor.md` ("One sentence, then the tools… one line
   per round of work"). So promoting narration visually is necessary but not
   sufficient: to get the richer "work out loud" beats the target surface
   implies, the **prompt's "Narrate As You Work" section must change too**. The
   exact content Claude Code shows *loud and inline* is the content Counselle
   *hides and clips to one line*. This is why it feels like "think, then answer."

**Goal:** one chronological stream — narration prose, tool-call widgets, and the
final answer, in the order they happened. Raw thinking (when enabled) collapses
to an expandable line. Each tool call is its own inline beat with a running→done
lifecycle, driven by data the tool returns for the UI.

**Non-goals:** rich per-tool widget design (a later pass — "super good" comes
later); the agent's reasoning/planning behavior itself; changing what tools
exist; MCP/skills surfaces.

## What Makes This Right (the Claude Code model)

Three visual roles, one vertical stream, in stream order:

1. **Thinking** — collapsed one-line spinner (`✻ Thought for Xs`). Raw
   reasoning hidden by default, expandable. Not the point.
2. **Loud talk (narration)** — normal prose shown inline as it streams. The
   agent saying what it is about to do.
3. **Tool calls** — compact inline affordances, each its own beat, interleaved
   with the narration, with a running→done lifecycle.

There is no separate "final answer zone" — the last prose block is just the last
beat. (Counselle keeps the final answer *citeable* — see Design Decision D2.)

### Target surface

```
┌ you ──────────────────────────────────────────────┐
│                    gather all info about harvard aid│
└────────────────────────────────────────────────────┘

  Let me look up Harvard's financial aid.          ← narration (visible prose beat)

  🔍 Web search · "Harvard financial aid"           ← tool widget: running → done
     5 sources · news.harvard.edu, college.harvard.edu +3

  Here's what I found on Harvard's aid program.    ← final answer prose (citeable)
  Families under $100k pay nothing; free tuition
  up to $200k… [1][2]

  ▸ Thought for 2s                                 ← ONLY if raw thinking is on;
                                                      collapsed, expand for reasoning
  📚 5 sources        [copy] [👍] [👎] [↻]
```

## Constraints

- Stack locked: FastAPI + pydantic-ai + LangGraph stream on the backend;
  React/Vite/TanStack Query + the existing SSE transport on the frontend.
- Honesty rule (AGENTS.md): never lie to a student. A failed search never gets a
  green check; a citeable answer must stay traceable to sources.
- The v1 event protocol is versioned; clients ignore unknown event types
  (`domain/events.py`), so adding an event type is forward-compatible.
- Reattach/replay, cancel, and persistence all consume the same event stream —
  any new event must survive buffering, replay (`app/turns.py`), and transcript
  reconstruction (`turn-reducer.ts` `transcriptEntryToEvents`).

## Premises (agreed 2026-07-07)

1. The target surface above is the visual end-state.
2. Narration = shown inline; raw thinking = collapsed/hidden by default.
3. Each tool call is its own inline beat with a running→done lifecycle, rendered
   by a widget registry keyed on tool/kind, with a good-looking default.
4. Simple now, built so widgets can get rich later. Tools return a structured UI
   payload for the frontend to draw from.

## Chosen Approach: B — Full event-model split + render rewrite

### Event model changes (`domain/events.py`)

- **`narration` (NEW event type):** the agent's loud talk. Model prose emitted
  while still working (before/between tool calls). Shown inline as visible prose
  beats. Replaces today's "route pre-final text into `thinking`."
- **`thinking` (semantics tightened):** ONLY native raw reasoning (Gemini thought
  summaries via `include_thoughts`). Collapsed by default, expandable. Emitted
  only when `thinking_summaries=True`.
- **`delta` (kept):** the final answer prose — the citeable, copyable block the
  sources rail attaches to (see D2).
- **`step` (+ `ui` field):** `StepData` gains optional `ui: ToolUi | None`,
  populated on the `end` event from a `ui` key the tool returns. Matches the
  existing `public_receipt` pattern (viz/overflow already do this).

### Backend (`app/steps.py` — `EmissionRouter`)

- Split the two text feeds cleanly:
  - Native `ThinkingPart` → `thinking` events (unchanged path, but now the ONLY
    source of `thinking`).
  - Pre-final `TextPart` (narration) → **`narration`** events instead of
    `thinking`. This is the relabel that fixes the "buried loud talk" bug.
- **Narrow, not delete, the gating.** Correction after reading the code: the
  final-answer phase is load-bearing beyond citations —
  `_FinalContentPlacementWriter` (`agent_node.py:217`) uses `on_final_start` →
  `start_final()` to buffer the final answer and inject viz at `<viz>` markers,
  and `FinalResultEvent` marks where `delta` begins. So final-answer detection
  and the `on_final_start` callback **stay**. What changes: pre-final `TextPart`
  routes to `narration` (always emitted, meant to be seen) instead of the
  `thinking` feed, so the thinking-vs-narration *classification* and its
  threshold buffering go away. Open risk to lock in eng-review: the
  `_final_candidate` hedge exists because `FinalResultEvent` timing can be
  ambiguous (is this run the answer or more narration?); confirm we can drop it
  without ever mis-emitting the true final answer as narration, or keep a
  minimal version.
- **Tool UI payload (needs a real model-hiding mechanism — reviewer correction):**
  add `ui_for(tool_name, args, content)` beside `detail_for`/`sources_for` to
  surface a `{widget, data}` dict onto `StepData.ui`. Two problems with the naive
  "tool returns a `ui` key" design:
  1. There is **no existing mechanism** that strips a tool-returned key from the
     model-visible payload — a raw `ui` key would go to the model verbatim (token
     cost + confusion). `public_receipt` is built *by* the overflow middleware and
     sent *to* the model inside the overflow envelope; it is not a hide-from-model
     convention. So define one: either a middleware allow-list that demotes/strips
     `ui` before the model sees the result, or carry `ui` on `public_receipt`.
  2. `ui_for` reading `content["ui"]` is **broken on overflow**: an overflowed
     tool's `content` becomes `{status:"overflow", public_receipt:…}` and the
     real dict is spilled to the store, so `content.get("ui")` is `None`. `ui`
     must be lifted onto `public_receipt` and dug back out — the exact pattern
     `sources_for` uses via `_search_source_content`/`_overflow_receipt`
     (`steps.py:389-396`). Make `ui_for` overflow-aware the same way.

### Frontend (`turn-reducer.ts`, `ChatMessage.tsx`, `AgentRunView.tsx`)

- **One ordered `segments` array** on `TurnState`, replacing the split
  `timeline` / `blocks`. Each event appends or updates a segment in arrival
  order:
  - `narration` → a `narration` prose segment (coalesced run).
  - `step` → a `tool` segment (start creates it, end/error updates it in place
    by `step_id`).
  - `delta` → an `answer` prose segment (coalesced).
  - `thinking` → a `thinking` segment (collapsed).
  - `viz` → a `viz` segment.
- **Render segments top-to-bottom in order** (`AssistantBody`). Narration and
  answer are prose beats (answer runs through `CitationRenderer`); tools render
  via the widget registry; thinking renders as a collapsed expandable line; viz
  via `VizBlock`.
- **Tool widget registry:** `widget key → component`, with a default fallback =
  today's `StepRow` (icon + label + one-line receipt + source chips) plus a
  running spinner while live. One example rich widget (e.g. `task_added`) proves
  the seam; everything else uses the default.
- `AgentRunView` stops being the whole-trace drawer; its per-step rendering
  moves into the inline tool widget. The only collapsible thing left is the
  `thinking` segment.

### Persistence / replay / citations (the gap my first draft missed)

The persisted turn record **throws chronological order away today**, so a
frontend-only fix would work live and re-flatten on reload. Confirmed:

- `build_turn_record` (`app/records.py`) stores three separate arrays —
  `steps: [...]`, `thinking: [...]`, `parts: [...]` (prose from `delta` only) —
  with no interleaving between them.
- `_assistant_entry_for_record` (`app/transcript.py:93`) serves them as
  `step_record: {steps, thinking, receipt}` + `parts`, still separate.
- `transcriptEntryToEvents` (`turn-reducer.ts:335`) replays **all steps, then
  all thinking, then all parts** — not stream order. On reload the reduce
  re-buckets into two zones regardless of the new render.

**Required for reloaded turns to render chronologically:** the record must
persist segment order. Design:

1. Add the `Emission` kind `narration` (`records.py:34`) and thread it through
   **all FOUR emission sites** (reviewer caught a missing one):
   - `app/run_turn.py:409-434` — **the sole writer-chunk → wire `Event`
     translator.** Its if/elif hard-codes `delta`/`step`/`thinking`/`viz`; a
     `narration` chunk falls straight through and is **silently dropped**, so
     narration never reaches the client and parked/error records (built from
     `run_turn`'s own `emissions`) lose it. MUST add a `narration` branch that
     both `emissions.append(("narration", text))` and `yield ev_narration(text)`.
     This was missing from the first draft and is implementation-blocking.
   - `_make_recording_writer` (`agent_node.py:294`) — record observer.
   - `TurnRegistry._observe` (`turns.py:503`) — cancel/watchdog record observer.
   - `build_turn_record` (`records.py`) — the builder.
2. `build_turn_record` gains an **ordered `segments` list** of **plain dicts**
   (NOT tuples — `app/state.py` msgpack-plain rule; persisting the raw `Emission`
   tuple stream would violate it). Each segment: `{"kind": "narration"|"step"|
   "thinking"|"delta"|"viz", ...}` in stream order. Keep `parts` (the citeable
   `delta` prose), `steps`, `thinking` as-is for backward compat + receipt
   derivation; `segments` is the new order-of-record. The segments builder MUST
   apply the same `FinalEmissionDeduper` viz-dedup the other consumers use
   (`build_parts`/`_observe`/`run_turn`/FE `appendViz`) or a reloaded turn
   renders a viz the live turn suppressed.
3. `_assistant_entry_for_record` serves `segments` on the wire entry;
   `transcriptEntryToEvents` replays from `segments` when present, falling back
   to the old steps→thinking→parts order for pre-existing records (forward-compat
   per the versioned protocol; old transcripts degrade to today's behavior, not a
   crash).
4. `derive_receipt` unchanged (counts steps; narration must not inflate it).
- Sources rail and citations continue to key off the `delta` answer parts (D2),
  so the "never lie / traceable" guarantee is unchanged.
- Frontend `model.ts` `assistantMessage` (derives `text=proseOf`, `activities`,
  `isThinking`, `timeline`, `blocks`) is rebuilt around `segments`; `types.ts`
  `TranscriptAssistantEntry` / `StepRecord` gain the `segments` + `step.ui`
  fields.

## Narration Quality Spec (v1 quality gate)

The improvement is a **refinement** of today's `counselor.md` "Narrate As You
Work" (lines 41-59), not a rewrite that breaks honesty. The existing rules are
already thoughtful (intent before tools; warm, specific examples; no findings in
narration). What makes it read thin: "**one sentence**," "narrate only intent,"
and no reaction after results. Quality narration keeps every honesty rule and
loosens exactly the things that make it robotic.

Target: narration reads like a calm, knowledgeable counselor thinking out loud —
Claude-Code cadence, Counselle voice.

**Loosen (the quality gain):**
- One or two natural sentences per round, not one clipped line.
- **Reactive, not just upfront.** Narrate intent before a tool AND a brief
  *operational* reaction after results before the next move — the flow becomes
  intent → tool → "that came back thin, trying the .edu site" → tool → answer.
  This reactive beat is where "work out loud" actually lands.
- Failure/retry is narrated out loud ("the database won't have this year's
  deadline — checking NYU's site directly"). The highest-signal beats.

**Keep (the honesty guardrails — non-negotiable, already in the prompt):**
- **No values/findings in narration.** Numbers, rates, dollar figures, names of
  values — those are cited content and live ONLY in the final `delta` answer with
  their `[n]` markers. Narration reacts at the *process* level ("five sources
  back, reading them"), never the *value* level ("Harvard covers full cost").
- No raw chain-of-thought / private deliberation.
- Exactly one final answer after tool work; never draft answer prose mid-work.

**Why this fixes the leak, not just the vibe:** the model currently dumps
operational talk into the answer because the prompt gives it no sanctioned place
for it. A first-class `narration` beat + "react here, not in the answer" guidance
gives that talk a home, which is the same fix as the "work out loud" feel.

**Eval-gated (this is what makes it v1, not a vibe check).** Add narration evals:
narration present per tool round; ≤2 sentences; **contains no `[n]` citation
markers and no tool-given values** (automated check — a value or marker in
narration is a honesty-boundary failure); no answer prose during tool work;
reacts to failures. Iterate the prompt against these + live beats until it passes.

**Model note:** `model_counselor = gemini-2.5-pro`. Narration cadence is a Gemini
behavior, and the observed leak is a Gemini tendency — so this needs
Gemini-specific eval iteration, not a one-shot prompt edit. Budget for that.

## Design Decision D2 — RESOLVED: keep a distinct citeable `delta`

**Decision (locked 2026-07-07):** keep `narration` and `delta` as separate feeds;
the final answer stays a distinct citeable block. Chosen on both quality and ease
— it preserves viz placement, citations, copy, sources, and the "never lie"
traceability, and it is *less* work than the dissolve (which cannot delete the
final-answer detection it promised to, because viz placement depends on it).

---

**Does the final answer stay a distinct `delta` block, or fully dissolve into
one prose stream?** The B option preview promised "drop final-answer gating; last
prose run = the answer" (full dissolve). After reading the code I recommend
**keeping `delta` as a distinct citeable final answer** (narration + delta both
exist), because the final phase is load-bearing in three places, not one:

- **Viz placement:** `_FinalContentPlacementWriter` buffers the final answer to
  inject visualizations at `<viz>` markers — it needs `start_final()`. Full
  dissolve breaks inline viz.
- **Citations + sources:** `[1][2]`, the copy button (`message.text`), and the
  sources rail all attach to the final answer; "never lie to a student" makes a
  traceable answer block a real requirement.
- Full dissolve forces reworking viz placement, citation anchoring, copy, and
  sources for little UX gain — the user sees one chronological flow either way.

So the gating machinery **narrows** (drop the thinking-vs-narration
classification + its threshold buffering) but the final-answer marker
(`on_final_start` / `FinalResultEvent`) **stays**. If you want the pure
Claude-Code dissolve anyway, say so and I will rework viz placement + citations
onto the whole prose run — but that is strictly more risk for no visible gain.

## Approaches Considered

### Approach A: Frontend-only chronological render
- Summary: rewrite reducer + render to one ordered flow, reuse today's events.
- Effort: M · Risk: Low.
- Pros: fastest, zero backend risk, ships the interleaved feel immediately.
- Cons: no tool→UI payload (widgets draw only from existing receipt/sources);
  narration and raw thinking can't be separated on the wire (both are
  `thinking`), so the "hide raw reasoning, show loud talk" split stays hacky.
- Reuses: `StepRow`, source chips, `CitationRenderer`, `VizBlock`.

### Approach B: Full event-model split + simplify (CHOSEN)
- Summary: add `narration`, tighten `thinking` to native-only, add `step.ui`,
  simplify the router's text gating, chronological render + widget registry.
- Effort: L · Risk: Med.
- Pros: semantically clean; deletes intricate gating code; first-class contract
  for the future rich widgets; the loud-talk/thinking split is correct at the
  source, not patched in the UI.
- Cons: touches the most delicate turn code (`EmissionRouter`) + its tests, plus
  persistence/replay/citation round-trip.
- Reuses: everything in A + the existing `public_receipt` convention for `ui`.

### Approach C: Hybrid — chronological render + tool-UI seam, defer router cleanup
- Summary: B's frontend + `step.ui`, but keep treating narration-as-thinking.
- Effort: M-L · Risk: Low-Med.
- Pros: full feel + tool widgets without EmissionRouter surgery.
- Cons: leaves the narration/thinking conflation in place; a second pass later.

## Recommended Approach

**B**, per the decision above, with **D2 resolved as "keep a citeable `delta`."**
The extra risk over C buys the correct source-level split (loud talk vs raw
reasoning) and a clean `step.ui` contract, which is the foundation the "super
good" future widgets sit on. Sequence the build to de-risk the delicate part:

1. Frontend `segments` reducer + chronological render behind the existing events

2. Backend: add `narration` event + relabel pre-final text; tighten `thinking`.
3. Backend: `step.ui` seam + one example widget (`task_added`).
4. Router gating simplification + persistence/replay/citation round-trip + tests.

## Success Criteria

- A turn that searches then answers renders as: narration → tool widget →
  answer, in that vertical order, streaming live (no "0.0s" flatten).
- No narration text ever leaks into the final answer block.
- Raw thinking (when enabled) is collapsed by default and never shown as prose.
- A tool returning a `ui` payload renders its widget inline; tools without one
  render the good-looking default.
- **Reloading the conversation reproduces the same chronological surface** (the
  record persists ordered `segments`; a live turn and its reloaded twin render
  identically). This is the criterion my first draft would have failed.
- Pre-`segments` transcripts still load (degrade to today's two-zone order, no
  crash).
- Inline viz still lands at its marker position in the final answer; citations,
  copy, sources rail unchanged.
- `EmissionRouter` loses its thinking-vs-narration classification; final-answer
  detection retained; tests green.
