## Problem Statement

The MVP3 frontend has four designed pages (Schools, Tasks, Essays, Activities) behind real auth, but every object renders from fixtures and mutates local React state. Nothing persists, the "Add school" button is dead (`SchoolsRoute.tsx:138`), school rows aren't clickable, and cross-object links are fake (essays reference schools by name string; tasks have no school link; school progress counts are hand-typed numbers). The goal: make the workspace fully working — backend, DB, full interactivity, no gaps — built so a future agent can do everything the user can do, with the UI updating live when it acts. Non-goals: the agent itself, chat, Calendar page, deploy, and quality-of-life features that don't affect the agent seam.

## Demand Evidence

Limited by design of this session (founder gave a formed brief; diagnostic skipped). Known evidence: MVP1 agent and MVP2 full-stack chat app shipped and verified against a live pipeline of ~2,746 schools; the founder killed and rebuilt the frontend around a workspace-first product thesis, which is a real bet, not a hypothetical. No end-user usage evidence yet for the workspace itself — see The Assignment.

## Status Quo

Students track applications in spreadsheets, Notion boards, and the Common App's own fragmented UI. Counselle's current prototype is visually complete but functionally a mock: a user who tries to actually plan their applications hits a wall on the first click.

## Target User & Narrowest Wedge

US college applicants (the existing Counselle user). The wedge for this build: a student can sign up, add their real schools from the live 2,746-school DB, and get a seeded, persistent, connected workspace where checking off work visibly moves their application progress. That loop working end-to-end with zero dead ends is the deliverable.

## Constraints

- Startup mode (AGENTS.md): KISS, value x ease, no speculative abstraction. The one carve-out: never lie to a student.
- Stack is locked: FastAPI backend, fastapi-users cookie-JWT auth, Postgres (Counselle owns its schema; pipeline DB is read-only), React/Vite/TanStack Query frontend, existing SSE infrastructure, ADR 0017 layering (service layer + thin API).
- The current visual design is approved; this build wires it, it does not redesign it.
- Chat/agent functionality returns later; nothing built now may block it.

## Premises (all agreed 2026-07-05)

1. Scope is exactly 4 pages (Schools, Tasks, Essays, Activities) + auth; Calendar stays a deferred placeholder.
2. Schools are added by searching the real pipeline DB; adding a school seeds its checklist tasks and essay slots.
3. Progress and essay counts become derived roll-ups, never hand-stored numbers.
4. Agent-ready = one API write path + actor recorded on every change + live change events. Those three now, nothing else agent-related.
5. All four object types get full CRUD, per-user scoping, undo on delete, and designed empty states — "no gaps" includes first-run.

## Approaches Considered

### Approach A: Thin CRUD, graph in the frontend
Four plain REST resources; frontend computes roll-ups from fetched collections; add-school seeding fired as follow-up creates from the browser; one coarse SSE "workspace changed → refetch" signal. Effort S-M, risk Medium. Pros: fastest to working; least backend surface. Cons: seeding logic in the browser means the future agent duplicates it; coarse refetch janks as data grows; roll-ups can disagree across pages during races.

### Approach B: Workspace service, graph owned by the backend (CHOSEN)
One backend workspace service owns objects, links, seeding, and roll-ups. "Add school" is a single transactional operation (school + checklist + essay slots). Every mutation records an actor (student | counselle) and emits a fine-grained change event (e.g. `task.updated`) on a **net-new workspace events SSE channel** built with the existing `sse-starlette` conventions (`api/sse.py`) — the MVP2 turn registry is per-turn streaming machinery and is *not* reused for this. HTTP routes are thin wrappers over the service; the future agent's tools call the same service functions. Effort M overall, with the events channel (per-user fan-out, multi-tab connection lifecycle, reconnect semantics) called out as its own line item — it is new surface, not a wrapper. Risk Low for CRUD/seeding, Medium for the events channel.

### Approach C: Event-log-first workspace
Every mutation is an appended event; state is derived. Perfect audit/replay, but L-XL effort, violates the repo's KISS rules, and the actor column + change events in B deliver the needed attribution at a fraction of the cost.

## Recommended Approach

Approach B. It is the only approach where "add the agent later without any issues" is literally true: agent tools and HTTP routes share one service layer, the same pattern the codebase already uses for `counselle_db` (ADR 0017). One hard constraint makes that true in practice: **service functions take explicit `user_id` and `actor` parameters** — never deriving identity from request-scoped cookie auth — so the agent can call them outside an HTTP request, exactly as `counselle_db/service.py` functions take explicit arguments today. Product shape of the end state:

- **Schools (the spine).** The stored entity is named the **Application**: a user-scoped row referencing the pipeline school's id — never a copy of pipeline data. Identity (name, location, logo) is read through the reference; **deadline, round, status, and list type are user-owned fields on the Application** (pre-filled only when trustworthy data exists, always editable, never a silent guess — per the never-lie rule, pipeline deadline coverage is ~8 of 2,746 schools, so deadlines cannot be "read from the DB"). Tasks and essays FK to `Application.id`, never to the pipeline school id directly.

  **The add-school flow** (the front door of the product, so it gets the polish): a command-palette-style dialog — open from the "Add school" button or a keyboard shortcut — with debounced typeahead over a new backend search endpoint that queries the pipeline school catalog (name + alias matching, per the school-identity rules in `docs/DATABASE_GUIDE.md`). Results show logo, name, location, and an "already on your list" state. Selecting a school flips the same dialog to a confirm step: choose round and list type (sensible defaults preselected), optionally enter the deadline, then one click fires a **single transactional backend operation** that creates the Application + seeded checklist tasks + essay slots. The row appears in the table optimistically; the change event confirms it. Built from the design system's existing primitives (command/combobox from the shadcn registry per AGENTS.md rules) — no custom search UI hand-rolled.

  Rows open a school detail side panel: status, list type, round, deadline, linked essays and tasks. Progress/essay columns are live roll-ups.
- **Tasks.** Existing three views wired to persistence; tasks link optionally to a school and essay; the existing `assignee: student | counselle` field is kept as the agent seam; drag, multi-select, and status changes persist. Note the deliberate distinction: `assignee` is a domain field on Task (who owns the work); `actor` is a separate audit attribute recorded on every mutation of **all four object types** (who made the change). They share vocabulary, not a column.
- **Essays.** Linked by `application_id` (nullable for the personal statement), deadline derived live from the linked Application's deadline field, editor autosaves persistently (current content only — version snapshots and version-browsing UI are both deferred to post-agent QoL, keeping Premise 4's "those three and nothing else" intact). Concurrent edits across tabs resolve last-write-wins (KISS); the change-events channel keeps a second open tab from drifting silently. `comments`/`suggestions` stay in the schema as the future agent's feedback channel, rendered as zero.
- **Activities.** Persistence, per-user scoping, ordering, Common App limit validation (already client-side), working copy-export. The "full story" layer is retained verbatim — it is future agent raw material.
- **Cross-cutting.** Designed empty states + add flows on all four pages; delete with undo everywhere; optimistic updates with rollback and error toasts; loading skeletons; per-user isolation via existing auth; every mutation attributable and broadcast as a change event so a second open tab (or the future agent) is reflected live.

### Future agent wiring (constraint on this build, not built now)

The repo already has one locked tool-handling pattern (ADRs 0004/0005/0012/0017): logic lives in an in-process service layer (`counselle_db/service.py`), the MCP server thinly wraps it for the LLM tool loop, and `app/` imports the service directly. **The workspace follows the identical pattern.** The new workspace service layer is the single home of all mutations; HTTP routes are its thin wrappers today, and when the agent returns, its workspace tools (add task, edit essay, add school, …) become thin wrappers over the *same* service functions — via the same MCP/toolset mechanism the counselle-db tools already use. Nothing about tool handling is invented or diverged: the agent gets workspace tools exactly the way it got database tools. Because service functions take explicit `user_id`/`actor` and every mutation emits a change event, agent-made writes flow to the open UI automatically with zero additional integration work.

## Open Questions

1. **RESOLVE FIRST — seeding-template and deadline source.** What is the default checklist per school, where do supplement counts/prompts come from, and what (if anything) pre-fills the deadline field (pipeline coverage is ~8/2,746 for CDS deadlines, so the realistic options are a static common-deadlines default table, user entry, or both)? This is the single biggest feasibility risk: the "add school → seeded workspace" loop is the deliverable. Answer before the add-school flow is finalized in the implementation plan.
2. School detail surface: side panel now vs dedicated page later — proposed side panel; confirm during implementation planning.
3. Delete semantics: deleting a school — cascade, orphan, or archive its linked tasks/essays? Proposed: soft archive with undo window.
4. Essay autosave cadence (version snapshots and version UI both deferred; only debounce/save timing needs deciding).
5. Common App field limits should be re-verified against the live form for the active cycle (noted in `domain/activity.ts`).

## Success Criteria

1. New account → empty states with working add flows on all four pages.
2. Add school via real DB search → seeded checklist + essay slots appear immediately.
3. Complete a task → the school's progress roll-up updates, including in a second open tab, without refresh.
4. Every object: create, edit, delete-with-undo, all persisted across refresh and scoped to the user; essay editor content autosaves (close the tab mid-draft, nothing is lost).
5. Every mutation goes through the backend API, records an actor, and emits a change event — verified by the two-tab test.
6. No dead controls anywhere in the four pages; frontend typecheck + tests and backend routine tests green.
